# Architecture — Behind the Smile

## System Overview

Behind the Smile uses a simple, deterministic NPC memory architecture to ensure that Maya — the game's central NPC — only references events that actually occurred in the player's playthrough.

This document explains how the system works and why each component exists.

## Key Design Decisions

### 1. Three Separate Data Categories

We explicitly separate **world facts**, **interaction memories**, and **relationship values** because:

- **World facts** are always true regardless of player choices. They represent the story's baseline.
- **Interaction memories** are the record of what happened. They are the source of truth for dialogue selection.
- **Relationship values** (trust, support_count) are convenient summaries but are NOT used to determine what happened. A trust value of 3 does not prove three specific actions occurred.

### 2. Deterministic Dialogue Selection

All dialogue is selected using GDScript `match` and `if` statements — not generated by an AI model. This means:

- The same state always produces the same dialogue.
- Every possible dialogue line can be read in the source code.
- There are no hallucinated or invented memories.
- Behaviour is fully testable and explainable.

### 3. Autoload Singleton Pattern

`MemoryManager` is registered as a Godot autoload, making it available everywhere via:

```gdscript
MemoryManager.record_interaction("offered_support")
MemoryManager.has_interaction("offered_support")  # → true
MemoryManager.get_valid_dialogue("later_interaction")
```

This is the simplest way to share state across scenes in Godot without complex dependency injection.

### 4. Rapid-Click Protection

The `_choice_lock` flag with a 0.3-second timer prevents the player from accidentally registering the same choice multiple times by clicking rapidly. This is paired with a `_transitioning` flag in `game.gd`.

### 5. Ending Construction

Endings are **built from actual interactions**, not selected from a simple lookup table:

```gdscript
func _build_supportive_ending() -> String:
    var parts: Array[String] = []
    parts.append("Through your actions today, you showed Maya...")
    
    if has_interaction("offered_support"):
        parts.append("When you sat with her in the courtyard...")
    
    if has_interaction("asked_feeling"):
        parts.append("By asking how she felt...")
    
    # Only interactions that actually occurred are mentioned
```

This ensures the ending text never describes something the player didn't do.

## How the Memory Log Works

The Memory Log UI (toggled by pressing **M**) calls `MemoryManager.get_memory_log_data()`, which returns:

| Category | Data |
|----------|------|
| **Established Facts** | Human-readable versions of world_facts |
| **Recorded Interactions** | Human-readable versions of interaction_history |
| **Relationship State** | trust, support_count, help_sought values |
| **Current Ending** | Only shown after reaching the ending scene |

The log ONLY displays interactions that are present in `interaction_history`. It never shows all possible interactions.

---

## What This System Is NOT

This is **not** a general-purpose AI or language model. It is a **deterministic, condition-based NPC memory system** that:

- Uses GDScript variables and dictionaries
- Selects pre-written dialogue using conditional logic
- Runs entirely offline with no external dependencies
- Can be fully understood and explained by a student

It solves Problem 09 by ensuring NPCs remember exactly what happened and never invent memories that contradict the established story or actual player choices.
